# 需求确认流程

本文件定义：**从毕设题目到可执行的功能需求清单的完整流程**。

> 前置阅读：本文件只管需求怎么定。代码怎么写看 `code-standards.md`，风格怎么选看 `style-integration.md`。

---

## 0. 核心原则

1. **不替用户做决定**：每个功能点都要经过用户确认
2. **不编造需求**：用户没说的功能不加，用户说的功能不漏
3. **分批确认**：一次问 3-5 个问题，不要一下问 20 个
4. **记录下来**：确认后的功能清单是后续开发的唯一依据

---

## 1. 从题目提取核心业务

### 1.1 题目分析模板

拿到毕设题目后，先做三层拆解：

```
题目：<用户给出的完整题目>

第一层 - 业务领域：
  这个系统是给谁用的？（学生/教师/医生/企业/普通用户...）
  解决什么实际问题？

第二层 - 核心功能：
  用户在这个系统里能做什么？（列出 3-5 个核心动作）
  哪个功能是"没它不行"的？

第三层 - 技术关键词：
  题目里有没有暗示特定技术？（如"基于大数据的"、"移动端"、"小程序"）
```

### 1.2 产品类型映射（用于后续风格选型）

| 毕设常见题目类型 | 产品类型关键词（用于 ui-ux-pro-max） |
|------------------|-------------------------------------|
| 在线教育/学习平台/考试系统 | education, learning management |
| 医院管理/挂号系统/电子病历 | healthcare, medical clinic |
| 图书管理/借阅系统 | library, digital library |
| 电商/商城/二手交易 | e-commerce, marketplace |
| 企业OA/人事管理/考勤 | enterprise HR, office management |
| 博客/论坛/社区 | blog, community forum |
| 任务管理/项目管理/协作 | project management, task tracker |
| 餐厅点餐/外卖 | restaurant, food delivery |
| 酒店预订/旅游 | hotel booking, travel |
| 物业管理/小区服务 | property management, community service |
| 财务/记账/账本 | personal finance, accounting |
| 问卷调查/投票 | survey, polling |
| 文件管理/云盘 | file management, cloud storage |

如果题目不在上面列表中，用题目的核心业务名词（英文）作为关键词。

## 2. 需求访谈模板

### 2.1 第一轮：整体把握（问 3-4 个问题）

```
根据你的毕设题目《XXX》，我先确认几个关键信息：

1. 用户角色有哪些？（如：普通用户 + 管理员，或学生 + 教师 + 管理员）
2. 最核心的功能是什么？（就是答辩时一定要演示的那个功能）
3. 有没有特殊的界面要求？（如必须适配手机端、需要大屏展示等）
4. 后端语言和前端框架有没有偏好的？（没偏好我按脚手架默认推荐）
```

### 2.2 第二轮：模块细化（按模块逐个确认）

脚手架已提供的基础模块（不需要重新讨论）：

- ✅ 用户注册登录（JWT）
- ✅ 用户管理 CRUD + 批量操作
- ✅ 操作日志自动记录
- ✅ 文件上传
- ✅ 公告/内容管理 CRUD

只讨论**新增的、业务特有的模块**。每个新增模块确认：

```
关于《XXX》模块：
  - 谁可以用？（用户 / 管理员 / 两者）
  - 主要数据字段有哪些？
  - 需要什么操作？（增/删/改/查/审核/导出/统计？）
  - 和其他模块有什么关系？
```

### 2.3 第三轮：边界确认（问收尾问题）

```
最后确认几个边界：
1. 数据库用脚手架已有的 scaffold_db，需要新建表吗？还是扩展已有表？
2. 有没有需要对接的外部系统？（支付/短信/邮件/第三方登录？）
3. 论文需要多少张系统截图？（默认不超过 10 张）
```

## 3. 功能需求确认单（输出模板）

三轮问完后，输出确认单：

```markdown
# 《XXX》功能需求确认单

## 技术方案
- 前端：Vue 3 + Ant Design Vue 4（端口 5174）
- 后端：Go + Gin（端口 8084）
- 数据库：MySQL scaffold_db
- 认证：JWT

## 用户角色
- 普通用户：<权限描述>
- 管理员：<权限描述>

## 功能模块

### 模块1：用户管理（脚手架已有，直接复用）
- ✅ 注册/登录（JWT）
- ✅ 个人信息维护
- ✅ 管理员：用户 CRUD + 批量操作

### 模块2：<核心业务模块名>
- □ 功能点 1：<描述>
- □ 功能点 2：<描述>
- □ ...

### 模块3：公告/内容管理（脚手架已有）
- ✅ 基础 CRUD
- □ 是否需要富文本：<是/否>

### 模块4：操作日志（脚手架已有）
- ✅ 自动记录
- □ 是否需要管理界面：<是/否>

### 模块5：文件上传（脚手架已有）
- ✅ 单文件上传
- □ 是否需要批量上传：<是/否>
- □ 文件类型限制：<图片/文档/视频/不限>

## 新增数据表（如有）
| 表名 | 字段概要 | 说明 |
|------|---------|------|
| xxx  | id, name, ... | <用途> |

## 不需要做的（明确排除）
- ❌ <功能>：<原因>

---
⬆️ 请确认以上内容。回复"确认"开始开发。
```

## 4. 确认信号识别

| 用户回复 | 含义 | 下一步 |
|---------|------|--------|
| "确认" / "可以" / "没问题" / "就这些" / "开始吧" / "OK" / "好的" / "行" | 需求已确认 | 进入阶段 1.5（风格选型） |
| "加上XXX" / "再加一个XXX" | 需要修改确认单 | 更新确认单后重新等待确认 |
| "不用XXX" / "去掉XXX" | 需要删除某功能 | 更新确认单后重新等待确认 |
| "XXX改成YYY" | 需要修改某功能 | 更新确认单后重新等待确认 |
| 沉默 / 不明确 | 用户未确认 | 追问"以上功能确认好了吗？确认后我就开始写代码" |

---

## 5. 需求变更处理

开发过程中用户提出变更：

| 变更类型 | 处理方式 |
|---------|---------|
| 新增小功能点（加一个字段/加一个按钮） | 直接加上，更新确认单 |
| 新增整个模块 | 重新走确认流程（输出更新后的确认单） |
| 删减功能 | 从确认单划掉，标注"已取消" |
| 该功能 | 确认单更新，已写代码需回滚的单独处理 |

## 6. 特殊场景

### 6.1 用户不给具体信息

> ❌ 不要说的：那你大概要什么功能？随便说说。

> ✅ 应该说的：毕设系统一般有这几个方向：管理后台类（如人事管理、图书管理）、展示类（如博客、作品集）、交易类（如二手市场、点餐）。你的题目偏哪个方向？我给你列几个典型功能参考。

### 6.2 用户要求的功能过于复杂

> 先确认核心功能，再提醒边界。比如用户要做"在线教育平台"全功能（直播+录播+考试+证书+支付+社交），应当说：

> "在线教育平台完整功能确实工作量不小。你看这样行不行：第一优先级做课程管理+视频播放+考试，保证答辩核心流程跑通。直播和支付作为论文里的'后续展望'部分。如果时间充裕再加。"

### 6.3 用户想用脚手架之外的技术栈

> "脚手架目前支持 React/Vue-Antd/Vue-ElementPlus/Vue-NaiveUI/uni-app 五种前端和 SpringBoot/Express/Flask/FastAPI/Go/.NET 六种后端。如果你想用的不在里面，建议先从里面选一个最接近的，保证基础功能先跑起来。"
