# 需求确认流程

本文件定义：**需求落地到确认单的执行细节**——确认单模板、确认信号识别、变更处理、难缠场景话术。

> **分工边界**（别把两份文档搞混）：
> - 需求访谈**方法论**（核心原则、题目三层拆解、角色定义、功能模块清单）→ 看 `feature-forge` skill
> - 需求落地的**脚手架细节**（本文件）→ 确认单长什么样、用户回什么算确认、改需求怎么处理
> - 代码怎么写 → `code-standards.md`；风格怎么选 → `style-integration.md`

四条需求原则（不替用户做决定 / 不编造需求 / 分批确认 / 确认单是唯一依据）定义在 `feature-forge` §0，本文件不重复，但**全程适用**。

## 2. 需求访谈模板

### 2.1 第一轮：技术栈与界面前提

角色与核心功能的提问走 `feature-forge` §2，选型依据走 `feature-forge` §1.1。回到这里只补两个**脚手架特有**的问题：

```
1. 后端语言和前端框架有没有偏好的？
   （没偏好我按题目类型推荐；只能从脚手架已有的里选）
2. 最终跑在什么设备上？
   浏览器  → frontends/ 下的 react / vue-antd / vue-elementplus / vue-naive
   微信小程序 → frontends/wxapp（原生）或 frontends/uniapp（跨端）
   手机 APP → frontends/uniapp 或 clients/rn
   桌面客户端 → clients/pyqt
```

### 2.2 第二轮：模块细化（按模块逐个确认）

脚手架已提供的基础模块（不需要重新讨论）：

- ✅ 用户注册登录（JWT）
- ✅ 用户管理 CRUD + 批量操作
- ✅ 操作日志自动记录
- ✅ 文件上传
- ✅ 公告/内容管理 CRUD

只讨论**新增的、业务特有的模块**。每个新增模块确认：

```
关于《XXX》模块：
  - 谁可以用？（用户 / 管理员 / 两者）
  - 主要数据字段有哪些？
  - 需要什么操作？（增/删/改/查/审核/导出/统计？）
  - 和其他模块有什么关系？
```

### 2.3 第三轮：边界确认（问收尾问题）

```
最后确认几个边界：
1. 新增的业务数据放新表，还是往 user / notice 里加字段？
2. 有没有需要对接的外部系统？（支付/短信/邮件/第三方登录）
3. 论文需要多少张系统截图？（默认不超过 10 张）
```

第 1 个问题的判断口径：

- **给 `user` 加字段是可以的**（如学号、班级、部门），但要同步改三处：建表 SQL、Spring Boot 的 `entity/User.java`、Express/Flask 的 `USER_COLUMNS` 常量
- **业务实体一律建新表**。不要把订单/课程塞进 `notice` 表用 `type` 字段区分，这种设计答辩时很难讲清
- **不要改现有字段的含义**。`role`、`deleted`、`create_time` 等已被鉴权层与 ORM 依赖，改了会连带坏现有四个模块

## 3. 功能需求确认单（输出模板）

三轮问完后输出确认单。**此模板与 `feature-forge` §5 是同一份东西**，差别只在于这里把脚手架已有模块的逐项取舍展开了。两处取其一即可，不要输两份。

核心要求：**新增业务模块必须用四要素表**（功能点 / 角色 / 对象 / 动作 / 权限），而不是一句话描述。理由见 `feature-forge` §3.3：只有拆到这个粒度，`database-designer` 才能推出表，`api-designer` 才能推出接口。

```markdown
# 《XXX》功能需求确认单

## 技术方案
- 前端：vue-elementplus（端口 5175）
- 后端：springboot（端口 8080）
- 数据库：MySQL scaffold_db
- 认证：JWT
- 产品类型关键词：<按 §1.1 映射表填>

## 用户角色与权限矩阵
| 角色 | role 值 | 能做什么 | 不能做什么 |
|------|--------|---------|-----------|
| 普通用户 | `user` | ... | ... |
| 管理员 | `admin` | 全部 | — |

## 复用脚手架模块（逐项取舍）

### 用户管理（已有）
- ✅ 注册 / 登录（JWT）/ 个人资料维护 / 修改密码
- ✅ 管理员：用户 CRUD + 批量删除

### 公告管理（已有）
- ✅ 基础 CRUD + 分页
- □ 是否保留富文本编辑器：<是/否>
- □ 是否改名为业务术语（如“系统公告”→“课程通知”）：<是/否>

### 操作日志（已有）
- ✅ 自动记录（标了日志注解的接口）
- □ 是否保留管理界面：<是/否>

### 文件上传（已有）
- ✅ 单文件 / 批量 / 类型与大小校验
- □ 实际用在哪：<头像 / 附件 / 封面图>
- ⚠️ 上限 10MB，白名单不含视频格式。需要传视频就改成存链接

## 新增业务模块

### 模块：<模块名>
| 功能点 | 角色 | 对象 | 动作 | 权限 |
|-------|------|------|------|------|
| 浏览列表 | 全部 | course | 分页查 | 登录 |
| 发布 | 管理员 | course | 新增 | 管理员 |
| 报名 | 普通用户 | enrollment | 新增 | 登录（仅本人） |

## 新增数据表
| 表名 | 字段概要 | 与其他表的关系 |
|------|---------|---------------|
| `course` | id, title, status, ... | — |
| `enrollment` | id, user_id, course_id, ... | user ↔ course 多对多中间表 |

## 页面清单
| 页面 | 路径 | 归属 |
|------|------|------|
| 课程列表 | `/course` | `views/user/` |
| 课程详情 | `/course/detail/:id` | `views/user/` |
| 课程管理 | `/admin/course` | `views/admin/` |

## 不需要做的（明确排除）
| 不做的 | 原因 | 论文里怎么写 |
|--------|------|-------------|
| <功能> | <原因> | 预留接口 / 后续展望 |

## 论文相关
- 系统截图：<N> 张（默认不超过 10 张）
- 密码明文存储，需在“系统不足与改进方向”一节说明

---
⬆️ 请确认以上内容。回复“确认”开始开发。
```

**确认单要落成文件**，建议存在项目根的 `需求确认单.md`。后续每个模块开发完要回头对照，`code-reviewer` 的功能完整性检查也靠它。

## 4. 确认信号识别

| 用户回复 | 含义 | 下一步 |
|---------|------|--------|
| "确认" / "可以" / "没问题" / "就这些" / "开始吧" / "OK" / "好的" / "行" | 需求已确认 | 进入阶段 1.5（风格选型） |
| "加上XXX" / "再加一个XXX" | 需要修改确认单 | 更新确认单后重新等待确认 |
| "不用XXX" / "去掉XXX" | 需要删除某功能 | 更新确认单后重新等待确认 |
| "XXX改成YYY" | 需要修改某功能 | 更新确认单后重新等待确认 |
| 沉默 / 不明确 | 用户未确认 | 追问"以上功能确认好了吗？确认后我就开始写代码" |

## 5. 需求变更处理

开发过程中用户提出变更时，**先改确认单，再改代码**。静默改代码会导致确认单失真，后面 `code-reviewer` 的功能完整性检查和论文需求分析章节都会对不上。

| 变更类型 | 处理方式 |
|---------|---------|
| 加一个字段 | 改建表 SQL + 实体类 + DTO + 表单 + 表格列 + 数据字典，五处同步 |
| 加一个按钮/操作 | 新增接口（走 `api-designer`）+ 前端 api 函数 + 页面调用，三处同步 |
| 新增整个模块 | 重新走确认流程，输出更新后的确认单，并重新评估体量（`feature-forge` §4.1） |
| 删减功能 | 从确认单划掉并标“已取消”；**已写的代码也要删**，残留的死代码答辩时会被问 |
| 修改现有功能 | 确认单更新；涉及已改过的表结构时，重建数据库而不是手写 `ALTER` |
| 改技术栈 | 已经写了代码后换前端/后端等于重做。先告知代价，用户坚持再换 |

**变更后必验一下**：新加的字段在列表页能看到吗？新加的接口页面上真的调了吗？只改了后端没改前端是最常见的半成品状态。

## 6. 特殊场景

### 6.1 用户不给具体信息

> ❌ 不要说的：那你大概要什么功能？随便说说。

> ✅ 应该说的：毕设系统一般有这几个方向：管理后台类（如人事管理、图书管理）、展示类（如博客、作品集）、交易类（如二手市场、点餐）。你的题目偏哪个方向？我给你列几个典型功能参考。

### 6.2 用户要求的功能过于复杂

> 先确认核心功能，再提醒边界。比如用户要做"在线教育平台"全功能（直播+录播+考试+证书+支付+社交），应当说：

> "在线教育平台完整功能确实工作量不小。你看这样行不行：第一优先级做课程管理+视频播放+考试，保证答辩核心流程跑通。直播和支付作为论文里的'后续展望'部分。如果时间充裕再加。"

### 6.3 用户想用脚手架之外的技术栈

> “脚手架目前有六个后端（springboot / express / flask / fastapi / go / dotnet）、六个 Web 与小程序前端（react / vue-antd / vue-elementplus / vue-naive / uniapp / wxapp），另外有两个客户端（clients/pyqt 桌面端、clients/rn 原生 APP）。如果你想用的不在里面，建议先从里面选一个最接近的，保证基础功能先跑起来。”

已经验证联调过的组合是 `springboot` / `express` / `flask` 配 `react` / `vue-antd` / `vue-elementplus`，**优先从这里推**。其余目录可用但未逐项验证，选它们要多花时间对齐接口与字段命名。

### 6.4 用户已经开始写代码了才来问需求

不要推翻重来。先把已有代码反向整成确认单（读一遍 `views/` 和 `api/` 就能列出已完成的功能点），标清 ✅ 已完成 / □ 待完成，再跟用户确认剩下的部分。这比“你先告诉我需求”高效，也不会浪费已有工作。
