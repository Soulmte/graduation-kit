# feature-forge

针对毕业设计的需求定义 skill。**当 graduation-project 进入阶段 1（需求确认）时调用**。

---

## 0. 核心原则

1. **不替用户做决定** — 只提供结构化的选项，让用户选
2. **分批确认** — 一次 3-5 个问题，不搞疲劳轰炸
3. **记录在案** — 确认后输出功能需求确认单
4. **脚手架优先** — 能用脚手架已有功能的，不做重复开发
5. **确认单要能被下游直接接手** — 它不是给人看的文档，是 `database-designer` 建表、`api-designer` 定接口的输入。模糊的“支持订单管理”无法推导出表结构，必须拆到**每个功能点 = 一个角色对一个对象做一个动作**

---

## 0.1 与下游的交接契约（先看这里）

确认单里的每一项都有下游接手人，不要写成无法落地的描述：

| 确认单字段 | 接手人 | 它需要什么粒度 |
|-----------|-------|---------------|
| 新增业务模块 | `graduation-project` 阶段 2 | 模块名 + 每个功能点一句话，能对应到页面 |
| 新增数据表 | `database-designer` | 表名 + 字段名与类型 + 表间关系（一对多/多对多） |
| 接口清单 | `api-designer` | 每个功能点对应的动作（分页/新增/改/删）+ 权限级别 |
| 角色与权限 | 三个后端的鉴权层 | **只能是 `admin` / `user` 两级**，见 §2 |
| 风格关键词 | `graduation-project` 阶段 1.5 | 产品类型词（后台/展示/工具），用于设计系统选型 |

## 1. 题目分析（Step 1）

拿到毕设题目后，输出三层拆解：

```
题目：《XXX》

┌─ 业务领域
│  谁用这个系统？解决什么问题？
│
├─ 核心功能
│  哪些是"没它不行"的功能？
│  哪些是"锦上添花"的功能？
│
└─ 技术倾向
    题目有没有暗示特定技术？
    （如"基于大数据"→ 需要统计图表）
```

### 1.1 技术栈选型（用户拿不定主意时）

只能从脚手架已有的里选，**不创建新技术栈目录**。判断依据按优先级：

1. **学校/导师有要求** —— 直接听，不用讨论
2. **题目形式限定** —— 题目含“微信小程序”→ `wxapp`（原生）或 `uniapp`（跨端）；含“APP”→ `uniapp` 或 `clients/rn`；含“桌面端”→ `clients/pyqt`
3. **用户自己熟悉什么** —— 答辩要能讲清代码，熟悉度比技术先进性重要
4. 以上都无 → 推荐 **Spring Boot + Vue-ElementPlus**，国内院校最常见，导师熟悉，资料多

一些硬信息供参考（不要拿这些去说服用户，只在被问到时回答）：

| 选型 | 适合 | 需知 |
|------|------|------|
| Spring Boot | Java 方向、导师要求“企业级” | 三个后端里层次最清，论文好写；需要 JDK 17 + Maven |
| Express | 前端背景、想全栈 JS | 手写 SQL，代码量最少，上手最快 |
| Flask | Python 方向、题目沉数据分析 | 手写 SQL；后续要接数据分析库时无缝 |
| React+Antd | 组件生态最全 | 本脚手架的 React 版用相对路径，无 `@/` 别名 |
| Vue-ElementPlus | 国内最常见，资料最多 | 默认推荐 |
| Vue-Antd | 想要后台感强一些 | 代码风格是 4 空格缩进 + 双引号，与其他两版不同 |
| Vue-Naive | 想要轻量现代风 | 消息提示靠 `window.$message`，写法略特殲 |

前后端可任意组合（接口协议完全一致），**但只能选一套前端**。多选一套就多一倍工作量，而论文里只能放一套截图。

## 2. 用户角色定义（Step 2）

**模板**：

```
这个系统需要几种用户角色？

A. 单角色（只有普通用户）
   适用：博客、记账、问答
   开箱可用，只是管理页面不对普通用户开放

B. 双角色（普通用户 + 管理员）⭐ 推荐
   适用：商城、医院挂号、图书管理、课程平台
   开箱可用，脚手架鉴权层就是为这个设计的

C. 三角色（学生 + 教师 + 管理员）
   适用：在线教育、教务系统、选课系统
   需要改鉴权层（约 6 处），工作量不大但不能漏，步骤见 §2.1
```

### 2.1 三角色以上的改造步骤

脚手架的 `user.role` 字段本身是 `VARCHAR(20)`，**存任意角色值都没问题**；限制在于鉴权代码把判断硬编码成了 `"admin"`。新增第三个角色（以 `teacher` 为例）要改下表全部位置，**漏一处就会出现“能登录但点什么都没权限”**：

| 序 | 改哪里 | 具体位置 |
|----|--------|---------|
| 1 | 数据字典 | `scaffold_db.sql` 里 `role` 列的 COMMENT 补上新角色；初始数据加一个新角色账号 |
| 2 | 后端鉴权注解/中间件 | Spring Boot `JwtInterceptor` 的 `!"admin".equals(...)`；Express `adminMiddleware` 的 `req.user?.role !== 'admin'`；Flask `admin_required` 的 `user.get('role') != 'admin'` |
| 3 | 新增角色守卫 | 不要改 `@RequireAdmin` 的含义，**新增一个**：`@RequireRole("teacher")` / `roleMiddleware('teacher')` / `@role_required('teacher')` |
| 4 | 前端路由守卫 | 路由 `meta` 里的 `requiresAdmin` 改为 `roles: ['admin','teacher']`，守卫里改成包含判断 |
| 5 | 前端菜单 | 侧边栏菜单按角色过滤，不能只判 `role === 'admin'` |
| 6 | 确认单 | 权限矩阵要列全三角色（见 §5 输出模板） |

**推荐的改法**：把硬编码的 `"admin"` 判断换成“角色白名单包含判断”，保留 `@RequireAdmin` 作为 `@RequireRole("admin")` 的简写。这样现有四个模块的代码一行不用改。

**建议先问用户一句**：“第三个角色能不能用‘普通用户 + 一个身份字段’表达？” 很多题目里的“教师”其实只是“能发布课程的用户”，用数据归属（`course.teacher_id = 当前用户`）就能解决，比动鉴权层更简单也更好讲。真的需要三角色时再按上表改。

## 3. 功能模块清单（Step 3）

### 3.1 脚手架已提供（不需重复开发）

| 模块 | 已有能力 | 边界 |
|------|---------|------|
| 用户管理 | 注册 / 登录（JWT）/ 个人资料维护 / 修改密码 / 管理员 CRUD + 批量删除 | 密码**明文存储**（毕设演示有意为之）；无验证码、无邮箱激活、无找回密码 |
| 公告管理 | CRUD / 分页 / 富文本（wangEditor） | 无审核流、无定时发布 |
| 操作日志 | 自动记录 / 条件查询 / 删除 | 只记标了日志注解的接口，密码参数已脱敏 |
| 文件上传 | 单文件 / 批量 / 类型与大小校验 / 路径遍历防护 | **上限 10MB**，仅允许图片/文档/压缩包，**不含视频格式** |
| 统计图表 | ECharts 已内置（React / Vue 三版） | uniapp / wxapp **没有** ECharts |

两个容易许诺过头的坑：

- **需求里写了“上传视频”** → 要改后端的扩展名白名单和 10MB 上限，而且毕设服务器存大文件不现实。建议改成“存视频链接”
- **需求里写了“验证码/短信/支付”** → 见 §4 边界确认，一律转为“预留接口”

### 3.2 需用户确认的业务模块

根据题目，列出候选模块让用户选择。以"在线教育平台"为例：

```
在线教育平台可能需要的功能模块：

□ 课程管理 — 发布/编辑/上下架课程
□ 章节管理 — 课程下的视频/文档章节
□ 学习进度 — 记录用户观看进度
□ 考试/测验 — 选择题/判断题 + 自动评分
□ 讨论区 — 课程下的问答讨论
□ 学习统计 — 学习时长/完成率图表

请选择核心模块（建议 ≤ 3 个，答辩够用就行）
```

### 3.3 功能点拆到多细才够（关键）

用户选完模块后，**每个模块要拆成能直接映射成接口的功能点**。拆到位的标志：能填满下面这张表。

以“课程管理”为例：

| 功能点 | 角色 | 对象 | 动作 | 对应接口 | 权限 |
|-------|------|------|------|---------|------|
| 浏览课程列表 | 全部 | course | 分页查 | `POST /api/course/pageQuery` | 登录 |
| 查看课程详情 | 全部 | course | 单条查 | `GET /api/course/getById/{id}` | 登录 |
| 发布课程 | 管理员 | course | 新增 | `POST /api/course/add` | 管理员 |
| 下架课程 | 管理员 | course | 改状态 | `PUT /api/course/updateStatus` | 管理员 |
| 报名课程 | 普通用户 | enrollment | 新增 | `POST /api/enrollment/add` | 登录 |
| 我的课程 | 普通用户 | enrollment | 列表查 | `GET /api/enrollment/listMine` | 登录（仅本人） |

这张表一出，三件事同时就确定了：

- **要建几张表** —— “对象”列去重就是表清单（course、enrollment）
- **要写几个接口** —— 直接交给 `api-designer`
- **要做几个页面** —— 按角色分组，普通用户的进 `views/user/`，管理员的进 `views/admin/`

**两个常被漏掉的东西**：

1. **关联表**。“用户报名课程”是多对多，需要中间表 `enrollment`，不能往 `course` 里塞个 `user_id`。拆功能点时遇到“某角色对某对象做标记/报名/收藏/评分”，就是关联表信号
2. **“仅本人”类权限**。`listMine` 这种接口权限写“登录”但实现时必须做归属校验（`api-designer` §2.8），确认单里要标清楚，否则开发时会漏

## 4. 边界确认（Step 4）

```
最后确认：

□ 需要对接外部系统吗？
  （短信验证码 / 邮件通知 / 微信支付 / 第三方登录）
  → 建议：毕设不需要真实对接，前端模拟即可，论文写"预留接口"

□ 需要数据统计/图表吗？
  → React / Vue 三版已内置 ECharts，后端加统计 SQL 即可
  → 选了 uniapp / wxapp 的要注意：**没有 ECharts**，需自行引入图表库

□ 有哪些明确不需要的功能？
  → 记录在"排除清单"中，并写好论文里怎么交代
```

### 4.1 体量自检（够不够毕设）

学生最容易走的两个极端：只做一个 CRUD 模块体量不够，或者列了七八个模块根本做不完。拉一个中间值：

| 指标 | 偏少 | 合理区间 | 偏多 |
|------|------|---------|------|
| 新增业务模块 | 1 个 | **2–3 个** | ≥ 5 个 |
| 新增数据表 | 1 张 | **3–5 张** | ≥ 8 张 |
| 新增接口 | < 8 个 | **15–25 个** | ≥ 40 个 |
| 新增页面 | < 4 个 | **6–10 个** | ≥ 15 个 |

加上脚手架自带的四个模块（用户/公告/日志/文件），落在合理区间就是一份完整的毕设。

**体量不够时优先加这三类**（性价比高、好写论文）：

1. **统计分析页** —— ECharts 现成，后端就是几条 `GROUP BY`，但看上去很“有东西”
2. **多条件组合筛选 + 导出** —— 展现 SQL 能力，工作量小
3. **一个多对多关联**（标签/收藏/报名） —— 能在论文里讲 ER 设计，比再加一个孤立 CRUD 有价值

**体量过大时优先砍这三类**：

1. 需要实时通信的（聊天、通知推送）—— 脚手架无 WebSocket，从零加成本高
2. 需要外部付费服务的（支付、短信、地图、语音）
3. “智能推荐”“数据挖掘”这类听起来厉害但说不清输入输出的 —— 除非题目明确要求，否则很容易在答辩时被追问到答不上来

## 5. 输出格式

```markdown
# 《XXX》功能需求确认单

## 技术方案
- 前端：[react / vue-antd / vue-elementplus / vue-naive / uniapp / wxapp]
- 后端：[springboot / express / flask / fastapi / go / dotnet]
- 数据库：scaffold_db
- 风格关键词：[后台管理 / 展示型 / 工具型]（交给阶段 1.5 选型）

## 用户角色与权限矩阵
| 角色 | role 值 | 能做什么 | 不能做什么 |
|------|--------|---------|-----------|
| 普通用户 | `user` | 浏览/报名/改自己资料 | 看用户列表、改别人数据 |
| 管理员 | `admin` | 全部 | — |

> 超过两角色时，在此补一句：本项目需按 §2.1 改造鉴权层（共 6 处）

## 复用脚手架模块
- [x] 用户管理（含修改密码）
- [x] 公告管理
- [x] 操作日志
- [x] 文件上传

## 新增业务模块与功能点

### 模块一：[模块名]
| 功能点 | 角色 | 对象 | 动作 | 权限 |
|-------|------|------|------|------|
| ... | ... | ... | ... | ... |

### 模块二：[模块名]
（同上表格）

## 新增数据表（交给 database-designer）
| 表名 | 字段概要 | 与其他表的关系 |
|------|---------|---------------|
| `course` | id, title, teacher_name, status, ... | — |
| `enrollment` | id, user_id, course_id, ... | user ↔ course 多对多中间表 |

## 页面清单
| 页面 | 路径 | 归属 | 说明 |
|------|------|------|------|
| 课程列表 | `/course` | `views/user/` | 卡片网格 + 分页 |
| 课程详情 | `/course/detail/:id` | `views/user/` | 独立路由，不用弹窗 |
| 课程管理 | `/admin/course` | `views/admin/` | 表格 + 内联编辑弹窗 |

## 非功能需求
- 密码存储：明文（毕设演示），论文“不足与改进”一节说明
- 文件上传：≤ 10MB，图片/文档/压缩包
- 分页：默认 10 条/页，上限 500

## 排除清单
| 不做的 | 原因 | 论文里怎么写 |
|--------|------|-------------|
| 微信支付 | 需商户资质 | 预留支付接口，前端模拟回调 |
| 短信验证码 | 需付费服务 | 同上 |

---
⬆️ 确认后开始开发
```

**输出前自检三件事**：

1. 每个功能点都能找到对应的表和页面（没表的功能是空话，没页面的功能用户碰不到）
2. 每张新表都至少有一个功能点在用它（建了不用的表答辩会被问）
3. 权限矩阵里普通用户的“不能做什么”不为空（全开放的系统体现不出权限设计）

## 6. 与 graduation-project 的配合

本 skill 被 `graduation-project` 在**阶段 1（需求确认）**时调用，产出功能需求确认单。确认单是后续所有开发的唯一依据。

**本 skill 产出后的流向**：

```
feature-forge 确认单
      ↓
【新增数据表】表  → database-designer 生成 DDL
【功能点】表      → api-designer 生成接口清单
【页面清单】      → 阶段 1.5 风格选型 + 阶段 2 按页面生成代码
【权限矩阵】      → 阶段 2 的鉴权标注与路由守卫
【排除清单】      → 论文“系统不足与改进方向”章节
```

**两个硬规则**：

1. **用户未明确确认前，不得进入下一阶段**。识别信号：“确认”/“可以”/“没问题”/“就这些”/“开始吧”/“OK”。其他回复一律当作继续讨论
2. **确认单要落成文件**，建议存在项目根的 `需求确认单.md`。后续每个模块开发完要回头对照，`code-reviewer` 的功能完整性检查也靠它

**需求中途变更时**：不要静默改代码。先更新确认单，标清变更影响到哪张表、哪些接口、哪些页面，再按新确认单开工。论文写到需求分析章节时靠的就是这份文档，中途丢了后面要重新逆向整理。
