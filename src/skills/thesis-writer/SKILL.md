# thesis-writer v2.0

本科毕业论文写作专用 skill，配套本项目（6 后端 + 6 前端多技术栈脚手架）。

---

## ⚠️ 铁律（AI 执行前必读，违反即重写）

1. **禁止写参考文献章节和任何文献引用标记**。正文中不得出现 [1]、[2] 或"XXX等[1]提出"
2. **禁止写目录章节**。目录由 Word 自动生成
3. **图表必须有编号和标题**。图下方标注"图X-Y 标题"，表上方标注"表X-Y 标题"
4. **图片文件按编号命名**。`图X-Y 名称.png`，编号 X=章号, Y=章内序号
5. **三线表只有顶线、表头下线、底线三条线**。数据行之间无横线，无竖线
6. **摘要正文在前，关键词在后**
7. **按章节分文件**。每章一个独立 .md 文件，放在 `docs/thesis/` 目录下
8. **生成完 MD 后必须自动运行** `convert/convert_to_docx.py` 生成 Word

## 工作流（严格按顺序执行）

### Step 1：确认输出目录

在项目根目录创建以下结构，如果不存在就创建：

```
docs/thesis/
├── images/    ← 所有 PNG 图片
└── canvas/    ← 所有 HTML 画布源文件
```

### Step 2：按章节生成（每章一个文件）

生成以下文件，严格按字数预算：

| 文件 | 章节 | 建议字数 | 核心内容 |
|------|------|---------|---------|
| `docs/thesis/00-摘要.md` | 摘要 | ~400字中文 + 英文 | 背景、方法、结果、关键词 |
| `docs/thesis/01-绪论.md` | 一、绪论 | ~2000字 | 背景意义、研究现状、内容目标、组织结构 |
| `docs/thesis/02-相关技术.md` | 二、相关技术 | ~2000字 | 技术选型理由、后端/前端/数据库简介 |
| `docs/thesis/03-需求分析.md` | 三、需求分析 | ~2500字 | 可行性、功能需求、非功能需求、用例分析 |
| `docs/thesis/04-系统设计.md` | 四、系统设计 | ~3000字 | 架构、功能模块、数据库（ER+表）、API接口 |
| `docs/thesis/05-系统实现.md` | 五、系统实现 | ~3800字 | 开发环境、后端/前端实现、关键技术 |
| `docs/thesis/06-系统测试.md` | 六、系统测试 | ~1500字 | 功能测试、性能测试、兼容性测试 |
| `docs/thesis/07-总结与展望.md` | 七、总结与展望 | ~800字 | 工作总结、不足、展望 |
| `docs/thesis/致谢.md` | 致谢 | ~300字 | 致谢 |

**全文总字数：12,000 - 20,000 字（本科标准）**。超出上限就压缩，不凑字数。

### Step 3：合并与转换

所有章节写完并确认后，执行：

```bash
cat docs/thesis/00-摘要.md docs/thesis/01-绪论.md docs/thesis/02-相关技术.md docs/thesis/03-需求分析.md docs/thesis/04-系统设计.md docs/thesis/05-系统实现.md docs/thesis/06-系统测试.md docs/thesis/07-总结与展望.md docs/thesis/致谢.md > docs/thesis/full.md
python .agents/skills/thesis-writer/convert/convert_to_docx.py docs/thesis/full.md docs/thesis/毕业论文.docx
```

## 格式规范

### 标题层级

论文正文使用以下标题层级，对应 Word 渲染样式：

| Markdown | 层级 | Word 样式 |
|----------|------|----------|
| `## 一、章节标题` | 一级标题 | 黑体小三居中加粗 |
| `### （一）节标题` | 二级标题 | 黑体四号缩进加粗 |
| `#### 1. 小节标题` | 三级标题 | 宋体小四加粗 |
| `**1）条目标题**` | 四级标题 | 宋体小四不加粗 |

### 图表规范

- **图注**：`![图X-Y 标题](images/图X-Y 标题.png)` — 渲染为图下方居中
- **表注**：`表X-Y 标题` — 渲染为表上方居中
- **截图标注**：与绘制图同格式 — `![图5-1 景点管理页面](images/图5-1 景点管理页面.png)`
- **编号**：X 为章号，Y 为章内序号，从 1 连续编号
- **正文引用**：每张图/表前后必须有文字说明。禁止两张图/表之间无文字
- **三线表**：markdown 表格自动渲染

### 插图配额（按项目实际表结构动态调整）

**绘制图（约 11 张，以实际表数量为准）**：
- 2 架构图（技术栈全景图、系统架构图）
- 2 用例图（普通用户、管理员）
- 1 功能模块图
- N 张实体属性图（每张数据库表一张，本项目 user/notice/operation_log 共 3 张）
- 1 张整体 E-R 图（只含实体+关系+基数，不含属性）
- 2 张流程图（JWT认证流程、用户登录流程）

- **截图应展示核心业务功能**，不使用登录页、个人信息等通用页面。截图标记用 `> 📷 **截图：xxx**`

**不画的内容**：
- JWT Token、角色、上传文件等非独立数据库表的"实体"不画 ER 图
- 操作日志记录、文件上传等辅助流程不单独画流程图（已在正文描述）
- 后端性能对比柱状图（用表格代替更精确）
- 公告模块的任何图

**实体属性图规则**：只画 `schema.sql` 中实际存在的数据库表。如项目新增表，按实际增补；如项目只有 3 张表，就只画 3 张。

### 插图占位符

正文中标注插图位置，截图与绘制图统一格式：

```
![图4-1 系统架构图](images/图4-1 系统架构图.png)
```

前后必须有说明文字，禁止连续两张图/表之间无文字。

## 写作风格

### 段落结构（每段必循）

每段按 3 要素组织：

1. **论点句**（1句）— 本段核心观点
2. **支撑句**（2-4句）— 具体数据、代码实例或研究观察
3. **收束句**（1句）— 回扣论点或引出下段

禁止：纯叙述无论点、论点堆砌无支撑、段尾悬空

### 章节论证差异化

| 章节 | 论证结构 | 避免 |
|------|---------|------|
| 绪论 | 现象→问题→方案 | 从定义开始 |
| 相关技术 | 选型场景→方案对比→本项目选择 | 逐一介绍每个技术 |
| 需求分析 | 用户场景→功能点→验收标准 | 功能列表罗列 |
| 系统设计 | 设计问题→方案→选择理由 | 只画图不解释 |
| 系统实现 | 目标→代码→踩坑→解决 | 只有代码无上下文 |
| 系统测试 | 测试目标→方法→数据→结论 | 只列数据不分析 |

### 连接词替换表

| 禁用的机械化连接词 | 自然替代方式 |
|-------------------|-------------|
| 因此 / 所以 | 前句结论直接引出下句，不加连接词 |
| 此外 / 另外 / 同时 | 用"还"、"也"融入句中，或分新段 |
| 首先...其次...最后 | 按时间线或逻辑链自然递进 |
| 然而 / 但是 | 用"实际测试发现"、"问题在于"等具体转折 |
| 综上所述 / 总之 | 段尾直接给结论，删掉 |
| 显然 / 显而易见 | 删掉，数据说话 |

### 禁用词黑名单（触发即改）

| 禁用词 | 替换为 |
|--------|--------|
| 综上所述 | 段尾直接给结论，不用过渡词 |
| 值得注意的是 / 显而易见 | 删掉，直接说事 |
| 随着...的发展 | 从具体问题切入 |
| 本研究 / 本文旨在 | "本项目做了..." |
| 具有良好的 XX 性 | 换成具体数据 |
| 进行了相应的处理 | 写具体做了什么 |
| 采用了...的方式 | "用了..." |
| 进行了...的处理 | "处理了..." |
| 实现了...的功能 | "做了..." |
| 针对 X 进行 Y | "对 X 做 Y" |
| 不仅...而且... | 拆成两句 |
| 首先...其次...然后...最后 | 用语义递进代替 |
| 因此 / 此外 / 另外 | 用自然转折代替 |
| 得到了广泛应用 | 给具体案例 |
| 具有重要的现实意义 | 给一个真实场景 |

### 句式硬性规则

- **句长**：> 40 字零容忍。优先拆为 2-3 个短句，每句 ≤ 20 字
- **句式多样**：混合简单句、复合句和插入语。避免连续 3 句以上相同结构，避免过于整齐的排比
- **主被动交替**：整章"被"字句 ≤ 15%，主动与被动交替，不堆砌任何一种
- **衔接自然**：禁止"首先/其次/然后/最后/因此/此外"。用问题引导、总结过渡、或语义递进代替
- **术语平实**：用日常用语解释技术概念，生僻词汇改用通俗表达
- **数据具象**：每个结论前必须有具体数字或实例。叙述数据时补充背景信息
- **段落过渡**：段间通过问题引导或上段总结自然过渡
- **核心一致**：重组句式时确保段落核心观点不变，改变的是表达方式而非内容

### 术语统一

| 推荐用法 | 不要用 |
|----------|--------|
| 脚手架 | 骨架、模板项目 |
| 多技术栈并存 | 多框架兼容、异构 |
| 前后端分离 | 解耦（指架构时） |
| 拦截器 | Filter（除非真的指 Servlet Filter） |
| 统一响应 | 通用返回、标准返回 |
| 操作日志 | 系统日志、用户行为记录 |
| 异步写库 | 非阻塞写入、延迟写入 |

### 分章节风格提示

- **摘要**：句子短（≤ 18 字），动词驱动，信息密度高
- **绪论**：不要"随着 XX 技术发展"开头；研究现状写具体项目名（RuoYi、SpringBlade 等）
- **相关技术**：每个框架 2-3 句，选型理由占一半，禁止抄官网文案
- **需求分析**：功能需求用动宾短语；非功能需求带数字（响应 < 200ms、并发 ≥ 500）
- **系统设计**：每个设计选择说一句为什么
- **系统实现**：代码片段 6-10 行，给具体类名/方法名
- **系统测试**：功能测试用表格；性能测试给具体数字
- **总结展望**：用自然文段，不列条目（禁止"一是...二是..."），展望 2-3 个方向各一段
- **致谢**：自然文段，不分点

### 整章自检表（每章写完必须逐项检查）

| 项 | 合格标准 | 检查方法 |
|----|---------|---------|
| 禁用词 | 黑名单词 0 次 | Ctrl+F 搜每个禁用词 |
| 超长句 | > 40 字句子 0 句 | 按句号切分统计 |
| 被动句 | 占比 ≤ 15% | 数"被"字句 |
| 段首套话 | 首句不用 5 类禁用开头 | 扫每段首词 |
| 结论有据 | 每个结论前有数据/例子 | 找"因此/所以"句验证 |
| 字数合规 | 在允许区间内 | 字符计数 |

## 绘图规范（速查）

### 技术路线

插图由 `reference/examples/` 下的绘图系统产出，三层结构，**改图只动数据层**：

- `editor.html` / `editor.js` — 可视化编辑器，浏览器打开即用，可拖元素、改文字、调字号线宽
- `engine/` — 绘图引擎，**不要改**
- `data/` — **只改这里**，每张图一个纯数据文件（声明 `nodes` 与 `links`）
- `verify.js` / `verify-editor.js` / `audit.js` — 校验脚本

- **Canvas 2D 绘制 + SVG 矢量导出**，拖入 Word 无限缩放不模糊
- 黑白线稿（`#000` 线、`#fff` 底），**禁用灰度和彩色**，这是学位论文规范
- 字号 14-16px（连线标签 12px），行距自动随字号缩放，不要写硬编码像素值
- PNG 导出 4 倍率，SVG 为真矢量
- 画布内无图标题、无图注（标题交给正文）

### 新增或修改一张图

1. 在 `data/` 新建或编辑数据文件，写 `nodes` 与 `links`
2. 在 `editor.html` 的 script 列表里注册新文件
3. 跑 `node verify.js`，**必须全绿才算完成**
4. 浏览器打开 `editor.html` 微调，导出到 `docs/thesis/images/`

**硬约束：所有可见元素必须写进 `nodes`。** 禁止用 `custom()` 钩子画内容，
否则编辑器选不中也拖不动（`audit.js` 会报）。

连线优先用 `{ from, to, fromSide, toSide }`，端点自动贴边并随节点移动；
只有需要绕行时才用 `{ points: [...] }` 写显式折线。**不要手写端点坐标**，
否则拖动节点后连线会脱开。

### 图型速查

| 图型 | 关键规则 | 数据文件 |
|------|---------|---------|
| 技术栈图 | 分层虚线框，层间箭头引用框锚点 | `01-framework.js` |
| 架构图 | 从上到下分层，虚线分组框内边距不小于 20px | `02-architecture.js` |
| 功能模块图 | 三层树，二级功能竖排文字，同层横干用 `midY` 统一 | `03-module.js` |
| 用例图 | 按角色分文件；include 虚线指向被包含用例，extend 指向基用例 | `04a` / `04b` |
| ER 属性图 | 实体居中，属性椭圆辐射排列，主键加下划线 | `05a`-`05e` |
| ER 整体图 | 只含实体+关系+基数，不含属性 | `06-er.js` |
| 流程图 | 圆角矩形=起止，矩形=处理，菱形=判断；异常分支单独成列 | `08-flowchart.js` |
| 时序图 | 泳道顶部矩形+竖虚线生命线；实线=调用，虚线=返回 | `09-sequence.js` |
| 性能图 | 柱状/折线，必须带数值标注，坐标轴有刻度和单位 | `10-chart.js` |

### 验收清单

前四项由 `node verify.js` 自动把关，不要手工目测：

- [ ] 连线端点紧贴元素边界，无空隙也无穿入
- [ ] 连线不穿过无关节点
- [ ] 改字号时行距跟着缩放
- [ ] 标签白底遮罩不瞎掉节点轮廓

人工确认：字号 14-16px、黑白无灰、画布内无标题图注、虚线框包住子内容、
底部无多余空白、文件名与正文引用一致。

详细字段契约与已知局限见 `reference/drawing.md`。

## 常见问题速查

**Q: 用户说"帮我写论文"但没给目录？**
→ 按本文件 §工作流 Step 2 的默认 8 章推进。

**Q: 用户要求画公告模块的图？**
→ 不画。回复建议改画用户表或操作日志表。

**Q: 用户要求写参考文献？**
→ 告知："本 skill 不生成参考文献，请您自行准备后插入。"

**Q: 字数超出 20% 怎么办？**
→ 用短句化规则精简：找超长句拆短，去掉冗余修饰词。

**Q: 写完某章不确定质量？**
→ 逐项走一遍 §写作风格 的自检表，≥ 2 项不合格就重写。

**Q: 关键流程图具体怎么画？**
→ 拄 `reference/examples/data/08-flowchart.js`，它是三列布局（主流程前半、后半、异常通道）的现成范例。

## 项目背景（硬编码，勿改）

本项目是一个"多技术栈并存"的 Web 脚手架系统，包含以下组件：

### 后端（6 个，端口与框架）
| 端口 | 框架 | 语言 |
|------|------|------|
| 8080 | Spring Boot 2.7 | Java |
| 8081 | Express | Node.js |
| 8082 | Flask | Python |
| 8083 | FastAPI | Python |
| 8084 | Gin | Go |
| 8085 | Minimal API | .NET 6 |

### 前端（4 个）
- React + Ant Design
- Vue 3 + Ant Design Vue
- Vue 3 + Element Plus
- Vue 3 + Naive UI

### 数据库（MySQL）
- `user` 表（13 字段）：id, username, password, nickname, age, gender, phone, email, role, avatar, create_time, update_time, deleted
- `notice` 表（6 字段）：id, title, content, create_time, update_time, deleted
- `operation_log` 表（8 字段）：id, username, operation, method, params, execute_time, ip, create_time

### 统一 REST API
- `/api/user/*` — 用户管理（JWT 认证 + CRUD）
- `/api/notice/*` — 公告管理（富文本）
- `/api/log/*` — 操作日志（AOP 自动记录）
- `/api/file/*` — 文件上传（校验 + UUID 重命名）
- `/api/health` — 健康检查

### 核心功能
- **用户管理**：JWT Token 认证、CRUD、角色分配、逻辑删除
- **公告管理**：富文本编辑、分页查询、软删除
- **操作日志**：AOP/中间件自动记录、异步写入、条件筛选
- **文件上传**：类型校验、大小限制、UUID 重命名、日期分目录

## 给 AI 的最后叮嘱

1. **SKILL.md 是唯一需要读的指令文件**。所有规则已嵌入，不需要再翻其他文件
2. **先确认目录再动笔**。`docs/thesis/` 和 `docs/thesis/images/` 不存在就先创建
3. **按顺序写**。从摘要开始，到致谢结束，别跳章
4. **写完一章自查一章**。走完自检表再进入下一章
5. **画图只改 `reference/examples/data/` 下的数据文件**，改完跑 `node verify.js`
6. **字数不是越多越好**。本科论文 12000-20000，超了就压缩
7. **所有章节完成后自动运行转换脚本**。不要等用户提醒
8. **禁止在 skills 目录下生成任何论文内容**。输出目录永远是 `docs/thesis/`
